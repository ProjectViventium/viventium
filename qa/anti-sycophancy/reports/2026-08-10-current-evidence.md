## Findings

### Current Source Corrections Proven

1. **No automatic foreground 180-second cutoff.** The synchronous GlassHive conversation-provider
   path leaves its response budget unset by default. An explicit request may set a turn budget; an
   operator may configure a 30–1800 second ceiling. Either path fails honestly and fences late output.
2. **Stop no longer expires after an unrelated 600 seconds.** A stopped graph-family fence now
   follows the provider-request retention lifecycle, which defaults to 30 days, and remains
   owner/tenant/family scoped. Repeated Stop renews that same lifecycle.
3. **Native citations become usable evidence.** The provider exports only structured public
   title/URL provenance from its private native ledger, renders normal Markdown links, and removes
   unresolved private markers and invalid control suffixes for both streaming and non-streaming
   output.
4. **Phase B preserves graph authorship.** When the top-level visible transcript already equals the
   concatenated structured consultant/Main text parts, cortex persistence keeps those parts instead
   of replacing the first part with the whole transcript.
5. **Agent Builder names the recall scope truthfully.** The switch now says “Limit RAG Conversation
   History to This Agent.” Off means the agent follows the user's global Conversation Recall
   setting; it does not mean recall is disabled. Deep Memory Search has this scope limiter off in
   source, so its always-background run can use the globally authorized conversation corpus.
6. **Background Cortex execution has no implicit 180-second cutoff either.** The compiler emits an
   execution timeout only when an operator explicitly configures one. When configured, the guard is
   that timeout plus a bounded grace window; when absent, no execution deadline is invented.
7. **Main completion is not Stop.** `generation_completed` leaves detached Phase B work alive to
   reach its own terminal state. Only explicit `user_cancelled` is treated as a user Stop and
   cancels that background work.

### Timeout And Lifetime Boundaries

These controls are intentionally separate:

| Control                                   | Current meaning                                                                                                                                    |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Foreground conversation-provider deadline | Unset by default; only explicit request/operator policy enables it.                                                                                |
| Stop-family fence                         | Provider-request retention lifecycle; 30 days by default, not 600 seconds.                                                                         |
| GlassHive callback wait                   | 600-second same-surface wait for long worker callbacks; it does not author-limit the foreground answer.                                            |
| Background Cortex execution guard         | Unset by default. An explicit operator setting enables timeout plus grace; runtime and stale recovery do not invent 180 seconds when it is absent. |
| Text/voice activation windows             | 1,300/690 ms background decision budgets; they are not Main-answer sleeps.                                                                         |

### Escaped Main-Last Failure And Crash Truth

- The escaped natural Web chain reached Reality Check and then Red Team, but the visible UI became
  idle/send-enabled at the Red Team transfer. No Main return or final synthesis appeared. Later
  evidence traced the final re-entry failure to an expired initialization-time signed capability
  bundle. The repaired runtime re-mints that authority immediately before every workspace-bound
  attempt; the post-fix natural and adversarial browser runs now pass `ANTI-003`/`ANTI-004` beyond
  the old 300-second boundary.
- Separately, three machine panic reports identify Python processes with roughly 9,500–12,300
  threads at kernel spinlock timeouts. GlassHive run metadata showed only a small number of queued/
  running workers with future capacity retries. The owning code trace showed a generic retry
  processor immediately resubmitting itself while the retry was not yet due, repeatedly creating
  new processor/timer work.
- This evidence supports a generic GlassHive capacity-retry scheduling defect. It does **not**
  support blaming Red Team, Red Team's prompt, the high-stakes prompt content, browser playback, or
  voice. Main-last graph closure and retry-thread safety are distinct defects and require separate
  regressions.
