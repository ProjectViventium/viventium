## Root cause

The escaped behavior required four failures to line up:

1. The fact existed in persisted memory, but the 1,800-token read ceiling and entry clipping omitted
   it from the bounded turn frame.
2. The GlassHive provider projected only external MCP-delimited tools and silently dropped the
   host-owned `file_search` capability.
3. Source-only/empty recall could be described as absence even when semantic retrieval was
   unavailable, making the transparency answer overconfident.
4. The independent control planes could look green separately. Prompt/config drift, QA identity,
   hardener load state, nightly delivery, provider capability, and observer/writer boundaries lacked
   one fail-closed joined integrity gate.

Two secondary regressions were found during measurement:

- Full resource metadata was serialized into the broker bearer token. A representative grant was
  20,411 characters and failed before MCP initialization with HTTP 431.
- The first recall eval could find static expected labels in old Workbench artifacts through native
  shell search. Its correct-looking response was rejected as false evidence.
- The exact-evidence validator compared raw Markdown to plain expected fragments, so harmless inline
  code formatting could falsely fail an otherwise correct provider-backed result.

The diversified correction exposed two more mechanism-level failures that the original named-entity
test could not reveal:

- The default local embedding route could miss a recent authorized cross-language paraphrase when
  semantic similarity was weak and lexical overlap was absent. The source was present and the index
  was fresh; treating one model's multilingual capability as a per-query guarantee was incorrect.
- GlassHive heartbeat JSON was rewritten in place. A concurrent service reconciler could read it
  while truncated, classify a live worker as orphaned, and persist an interrupted result even though
  the worker later completed correctly. The 8/9 pre-fix matrix caught this exact race.
- A real browser turn with recall disabled still returned the hidden synthetic fact. The provider
  had correctly projected no recall resource, but the full-access worker used eight shell commands
  to search private app/runtime state and treated the match as conversation evidence. This was a
  correct-looking false pass: no broker call occurred, the UI took about 80 seconds, and the answer
  crossed an authorization/provenance boundary.

The nightly failure had a separate launcher boundary: resolving the host CLI from a symlink selected
the wrong sibling companion path, so the worker could not produce the required proof artifact.

The joined integrity rerun exposed why the hardener itself could regress after an apparently healthy
install: noncanonical test/side-by-side config writes compiled their own intentionally disabled
hardener setting, but automatic sync still applied it to the single user-level LaunchAgent. A release
test reproduced the production drift by removing the real schedule.

The independent Claude review found five further mechanism-level defects that the first pass had
not covered:

- the historical ceiling was 1,800 tokens (not 2,200), and the schema still defaulted to 1,800
- the provider sent bootstrap HMAC/timestamp headers that the GlassHive receiver never verified;
  the same envelope could override reserved host env and had no encoded-size limit
- brokered `file_search` projected inline `.files` but omitted ACL-resolved knowledge-base
  `.file_ids`
- read selection used a character approximation against storage limits enforced by the real
  tokenizer, and an oversized single segment could collapse to an omission marker with no content
- the new cognitive-integrity observer instantiated ordinary schedule storage, whose initialization
  can reconcile stale live runs and therefore was not actually read-only

A final review-only pass correctly placed the work on hold again after the first green matrix. It
found that the recent-turn safety net could still compete with semantic evidence and that the eval
bank did not bind every result to fresh nonce evidence or reject every native command. Strengthened
live evaluation then caught a multilingual answer that was textually correct but had first tried a
native shell search using a storage-like recall-resource label. Those correct-looking results were
treated as failures and repaired rather than accepted.

The review also found incomplete writer/read failure transparency, a reconnect health-gate delay,
a hardener rollback crash window/PID-reuse wedge, and a delegated-worker host-tool parity gap.

Real browser acceptance then exposed two more universal defects rather than prompt defects:

- the provider treated an honestly empty, policy-authorized capability projection as if signed
  bundle minting had failed, making an ordinary tool-free turn fatal
- LibreChat startup logged the fully interpolated custom config instead of a structural summary,
  placing provider credentials in an owner-only local log

The final native Telegram rerun exposed one more provider-boundary defect. Conversation-mode
GlassHive correctly refuses to rewrite instruction files in the user's workspace, but the broker
routing brief existed only in those bootstrap instruction fields. The signed broker and recall
resources reached the worker while the service-backed-resource guidance did not reach the actual
developer-authority message. Presented with recall filenames, the worker could therefore try local
filesystem discovery instead of calling the host tool.

## Aligned repair

- Saved-memory reads use an 8,000-token total ceiling with explicit per-key budgets, whole-entry
  selection, and model-visible omission/boundary metadata.
- LibreChat resolves host-owned tools after provider initialization and publishes them to GlassHive
  through a signed broker MCP. The broker uses the same canonical `file_search` implementation as
  native routes.
- Broker grants contain a bounded digest reference; full validated scope is kept server-side in a
  bounded cache and revalidated during hydration. The representative grant is now 942 characters.
- Worker-native tools remain declared and available. A recall acceptance run must prove the broker
  tool actually completed and that no native command ran; universal shell stripping would reduce
  legitimate workstation capability and is not the product fix.
- Recall distinguishes successful empty retrieval from an unavailable/inconclusive semantic path.
- `bin/viventium cognitive-integrity --json` joins source/live prompt and config parity, memory
  ceilings, provider transport, QA account safety, hardener health, Workbench nightly status,
  GlassHive companion readiness, and Codex observer-only boundaries.
- The nightly compiler and GlassHive profile canonicalize a symlinked host CLI before resolving its
  companion. The Workbench remains the nightly writer, the direct hardener remains the memory writer,
  and the Codex automation remains an observer.
- Automatic hardener schedule sync now runs only for canonical installed App Support. Noncanonical
  config tests use isolated home directories and a sentinel regression proves they cannot mutate the
  one user-level LaunchAgent.
- Cross-conversation eval fixtures use a fresh random nonce, insert a real prior conversation for the
  isolated QA account, and join the response to the exact request/run/worker stdout ledger. Cleanup is
  guarded and private output is represented only by counts and hashes.
- Exact-evidence comparison normalizes presentation-only Markdown and whitespace before checking
  required fragments; provenance and tool-execution gates remain strict.
- When all authorized source/lexical overlap is weak and semantic recall returns no candidate,
  `file_search` may expose at most one latest eligible prior turn in the same scoped corpus as
  negative-weight fallback evidence. It never evicts a retrieved result, never expands into adjacent
  turns, receives no raw-message or user-authorship bonus, and is removed before fusion whenever any
  semantic candidate exists. It preserves all active-thread/expiry/Listen-Only exclusions and
  contains no entity, language, provider, or prompt-specific branch.
- Exact/verbatim recall requests preserve every content-bearing token in the requested span,
  including opaque identifiers, dates, numbers, punctuation, and casing; translation applies only
  outside that literal span.
- GlassHive heartbeat, active-session, and session-key state is published through atomic private-file
  replacement. Cross-process reconciliation therefore sees the previous complete state or the next
  complete state, never a partial JSON document.
- Acceptance is category-based and provider-independent: nine synthetic classes exercise the
  GlassHive-backed main route and four independently exercise direct xAI voice/native
  `file_search`. Source/upload digests must be fresh, broker/native tool provenance must match the
  route, and model guessing or workspace evidence substitution fails the run.
- Conversation-provider turns now derive a missing-resource evidence boundary from structured host
  tool/resource state. When a configured host tool has no authorized resource, the worker is told
  not to imitate it through app state, exports, caches, logs, backups, hidden runtime folders, or
  unrelated workspace copies. Native filesystem capability remains available for ordinary
  user-scoped project work; there is no entity, prompt, provider, or account-name branch.
- Host-owned recall and transcript resources are advertised to the model as virtual service
  evidence rather than storage-like filenames. The worker is explicitly forbidden from treating
  those labels as mounted paths, and the strict live gate rejects any native command in a
  broker-recall case even if the final text is correct.
- GlassHive now verifies the bootstrap HMAC and bounded timestamp before decode, rejects envelopes
  above 128 KiB, and excludes reserved host env in every deployment mode. Conversation and delegated
  workers use ACL-primed `.file_ids` plus `.files`; declared capability materialization fails closed.
- Memory reads trust plausible persisted tokenizer counts, retain bounded head/tail evidence for an
  oversized single segment, and treat stale counts defensively. Panel writes invalidate the read
  cache. Per-turn read and writer outcomes produce privacy-safe App Support receipts consumed by the
  joined integrity gate.
- Cognitive integrity opens scheduling state in explicit SQLite read-only mode and honors the
  selected App Support root. The hardener schedule owner itself rejects noncanonical roots derived
  from a spoofed `HOME`; rollback revisions are persisted after every mutation and locks bind PID to
  process-start identity.
- Conversation-provider bootstrap now distinguishes `no authorized capability` from `declared
  capability failed to mint`: the former continues without advertising a tool; the latter still
  fails closed. Startup config logging emits names/shape only and regression tests prove a sentinel
  credential is absent from every info/debug call.
- Conversation-provider bootstrap carries its capability-routing contract as a distinct signed
  field and LibreChat appends it to the real developer-authority message before the final dynamic
  state tail. Service-backed resource labels are explicitly not treated as mounted files; when the
  authorized host tool covers the evidence, it is called before filesystem discovery. This rule is
  capability-structural and contains no user entity or prompt match.

## Research and ceiling decision

The design follows three current constraints:

- Long contexts do not guarantee reliable use of facts placed in the middle, so the system uses a
  bounded high-signal memory frame plus retrieval rather than treating the model context window as a
  database: [Lost in the Middle](https://arxiv.org/abs/2307.03172).
- Contextualized hybrid retrieval materially improves retrieval quality, supporting the existing
  lexical-plus-semantic path and truthful degraded modes: [Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval).
- Qwen3-Embedding officially supports more than 100 languages and query-side instructions, but its
  model card is a capability statement rather than a perfect-recall guarantee. The current 0.6B
  default remains the measured local cost/quality choice; query-instruction asymmetry is a future
  benchmark option, not an unmeasured index change: [Qwen3-Embedding-0.6B model card](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B).
- The current MCP specification makes tool availability explicit and authorization-dependent per
  request; providers cannot be assumed to inherit a host capability without a declared transport
  and scoped authorization: [MCP 2026-07-28 tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools).
  Viventium's signed scoped broker follows that boundary, but this repair does not claim a wholesale
  MCP 2026-07-28 SDK/protocol migration; the repository still pins the 1.x SDK and that breaking
  migration requires its own compatibility plan and QA.

The 8,000-token memory frame is a measured product ceiling, not an invitation to keep expanding the
prompt. It raises the prior 1,800-token bottleneck while leaving the majority of modern model context
for current dialogue, tools, sources, and generation. If this ceiling becomes insufficient, retrieval
quality and selection should improve before another unconditional expansion.

## Acceptance status

The current continuity read and cross-provider recall paths pass the diversified local acceptance
matrix and the earlier headed Workbench, authenticated browser, and native Telegram checks. This is
evidence for those categories and routes, not a universal-memory guarantee. Overall cognitive
freshness is still `PARTIAL`: immediate per-turn memory writes are degraded until the connected
account is restored or an architecture-safe writer fallback with full mutation-tool parity is
implemented and proven. Reconnecting an account is a user-controlled credential action and is not
performed silently. The latest explicit Workbench rerun is successful, but it does not retroactively
turn the failed Aug 8 unattended fire into a scheduled pass; the next automatic run is still a live
acceptance gate. Protected live Agent Builder drift likewise remains unmodified pending review.

Future startup logs no longer receive interpolated secrets. Historical entries remain only in an
owner-readable local log and were not copied into public evidence; destructive log removal and any
credential rotation are intentionally not performed without user approval.

The review-only Claude audit is incorporated. It independently challenged the RCA, security,
control-plane mutation, tokenizer, delegation, automation, ranking, and evidence claims. Its final
hold on the weak-fallback ranking and underpowered eval gates was cleared only after the 101/101 and
52/52 regressions plus a fresh 9/9 strict live run. Remaining non-incident ceilings are still listed
as gaps rather than silently closed. Conversation-provider
broker grants were also reduced from a 24-hour effective renewable window to 1 hour. Read-only tool
calls remain reusable within that bounded run window by design; write calls require signed
confirmation plus single-use invocation ids. This dirty nested
source state is not a shipped release: LibreChat and GlassHive commits plus parent component-pin
updates require separate user approval before fresh clones can receive the repair.
