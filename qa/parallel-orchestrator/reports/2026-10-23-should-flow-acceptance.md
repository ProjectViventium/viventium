## Capacity failure and recovery

New worker admission correctly rejected work when the host crossed its saved disk-space safety
limit. Existing work remained separate and completed. Reclaiming regenerable package caches through
their own official commands restored admission; no saved threshold, source, installed environment,
user file, credential or personal state was changed. An in-use cache lock was honored. The next
browser worker started and truthfully returned a connection refusal rather than inventing a heading.
This local hardware constraint is distinct from a provider or tool failure.

Later disk exhaustion stopped the local container engine and Redis. Core could not remain up
without Redis. The engine's own log identifies an out-of-space shutdown; supported Desktop recovery
restored Redis and Core without removing containers, volumes or project files. The user then freed
space above the saved guard. Admission recovered, followed by the successful current/historical
audio, two-worker Web and real PCM call checks above. Saved thresholds were unchanged.

The same incident exposed the warm-Main preflight and deadline-classification defect above. Real
source messages were retained, but Grok never started. The final correction passed independent
evidence-led review. The new low-disk message on the real user surface is NOT RUN after physical
recovery; its evidence is causal unit and HTTP/streaming checks. Healthy loaded-path acceptance is
recorded separately above.

The shared attachment formatter now emits file facts without telling a coordination-only executor
to read local workspace paths it cannot access. Existing registered worker contracts continue to
own file/tool use. There is no modality-specific routing or new prompt fallback.
