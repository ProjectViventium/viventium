# Parallel Work QA Cases

## Locked Queen Bee and Worker Bee regression contract

The normative user experience is the current
[Parallel Work capability contract](../../docs/requirements_and_learnings/capabilities/parallel-work.md), including automatic ordinary use without opt-in, and the retained
[locked Queen Bee and Worker Bee contract](../../docs/requirements_and_learnings/55_Parallel_Work_Orchestration.md#locked-queen-bee-and-worker-bee-user-experience).
Every implementation, review, and release claim must preserve the full contract below. A narrow
technical pass cannot override a failed user outcome.

The HTML journey is one transport and artifact check. It cannot accept general Worker capability.
Include ordinary app/computer actions and non-file outcomes, actual installed-child OS permission
use, signed-in account access, and channel delivery. Use natural varied goals without telling Main
when to delegate. Preserve every native capability permitted for the task; no HTML-only tool set,
prompt recognition, or artificially reduced harness may satisfy these cases.

delivery, duplicate work/results, and lost work after restart. Any one is a case failure and keeps
Parallel Work **PRE-GATE / NOT READY**.

## Release rule

Run `bin/viventium release-check`. Every `PWK-*` and `REL-*` catalog row plus cross-owner `TR-026`,
`EMO-UC-047`, `EMO-UC-048`, `MPV-061`, and `TGDOC-010` is required. A Markdown `PASS` closes no gate without one fresh,
unique, candidate-bound structured receipt for that exact case and installed artifact. Any missing,
stale, duplicate, mismatched, unknown, `NOT RUN`, `FAIL`, `PARTIAL`, or `BLOCKED` result exits nonzero
and forbids Ready or Complete wording. The gate verifies the declared availability and default mode;
it does not replace ordinary automatic delegation with an opt-in requirement. An explicit focused
preference and actual runtime capability restrictions remain authoritative.

A release PASS additionally requires externally trusted publisher and producer signatures, exact
signed service acknowledgements where applicable, and a non-rollbackable witnessed outcome ledger.
An owner-readable local HMAC is valid only for explicitly labelled pre-gate QA and can never produce
READY. Missing independent trust, replayed evidence, forged service identity, or a later failed
outcome keeps the exact case open.

For `TR-026`, `EMO-UC-047`, `EMO-UC-048`, `PWK-UC-016`, `PWK-UC-017`, and `REL-UC-004`, a `PASS`
receipt also requires the exact case's live Core, GlassHive, and/or Telegram processes to restart
after activation and write valid HMAC acknowledgements. The receipt stores only their combined
`serviceAckDigest`. Missing, stale, forged, replayed, dead, replaced, or partial process proof fails closed.

Local development may use only `bin/viventium release-check --local-qa --json`.
It permits pre-gate QA without changing source defaults and must be labeled **PRE-GATE / NOT
READY**. Unit/mocked tests support but do not replace the real Telegram, browser, voice, scheduler,
native harness, restart, and installed-runtime cases above.
