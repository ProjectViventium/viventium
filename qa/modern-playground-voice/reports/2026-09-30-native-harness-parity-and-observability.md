## Measured latency and streaming

The former 19–25 second range came from individual checked turns, not a percentile benchmark.
The joined 19.96 second typed file-read sample breaks down as follows:

| Stage, from dispatch | Seconds |
| --- | ---: |
| Submit, admission and time before native execution | 2.08 |
| Native execution, start to end | 17.20 |
| Native end to first answer delivered to gateway | 0.21 |
| First answer to first audio | 0.47 |
| Total | 19.96 |

The long outer harness tool span was not file-read I/O time. The real injected-microphone baseline
took **14.51 seconds on the SDK's speech-end-to-speech-start metric**: native execution was 11.37 seconds,
including approximately 1.52 seconds opening the session. Gateway first-token latency was 12.71
seconds and TTS node time to first byte was 0.44 seconds. End-of-utterance, transcription and
dispatch metrics overlap; their durations must not be blindly added. The gateway's speaker-context
end marker gives 13.70 seconds for this same sample, about 0.81 seconds less. It may use final
transcription observation time. Actual input PCM and browser playout clocks must be joined before
claiming user-perceived latency. Core's first reasoning delta carries native execution activity
summaries; it is not evidence of the model's first reasoning token.

Same-authority native ACP smoke tests verified both exact models at **High** effort:

| Model | Session setup | First answer chunk after prompt | Prompt completion | First chunk → completion |
| --- | ---: | ---: | ---: | ---: |
| Grok 4.7 Fast | 0.68 s | 16.98 s | 17.82 s | 0.84 s |
| Grok 4.7 | 0.29 s | 35.49 s | 36.90 s | 1.41 s |

These are diagnostic samples without projected tools, not complete call benchmarks. The answer
arrived in bursts lasting 0.53 and 1.16 seconds. Fast also had a 10.75 second gap after visible
reasoning. Hidden reasoning, provider queueing and prompt-cache behavior are hypotheses, not
measured causes. High effort was retained.

**Yes, the current Voice answer path waits for the completed native envelope/run.** ACP already
delivers message chunks before its terminal response. Native structured delivery buffers ordinary
content, and LibreChat explicitly refuses authored previews on Voice. Removing that guard alone
would not provide safe accepted-answer streaming. It could speak text before graph/Voice delivery
control, later tool activity or final validation. Speech cannot be unsaid.

The smallest credible streaming change is to carry typed answer commitment, delivery disposition
and revision identity through the existing native → Core SSE → TTS path, then emit only answer
content with valid authority. Preserve tool approvals, declared silence, fallback, supersession,
cancellation and the final receipt. Do not send reasoning, partial JSON or pre-tool placeholders to
speech. The measured first-chunk head start is only 0.84–1.41 seconds in these samples; streaming
alone cannot remove the earlier silence. Also measure session reuse/setup and Core time outside
the native run. Prompt changes require the normal Prompt Workbench lineage and exact-model A/B.
